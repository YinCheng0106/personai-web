# PersonAI 夥伴開發與專題展手冊

> 給第一次一起做網站、剛開始使用 GitHub，或需要上台介紹 PersonAI 的夥伴。
>
> 閱讀順序：先看懂 → 照著做 → 能說明。看不懂名詞時，直接跳到[小小字典](#小小字典)。

## 先用 30 秒認識 PersonAI

**PersonAI 是協助使用者訓練的 AI 健身教練網站。**

使用者選擇深蹲或伏地挺身後，網頁會用相機與 MediaPipe 找出人體的 33 個姿勢關鍵點。網頁不把相機影片送到後端；它只把這 33 個座標傳給後端。後端會計算角度、判斷動作階段、計次、提示可能的姿勢問題，並估算卡路里。訓練結束後，紀錄會儲存並顯示在首頁與歷史頁面。

### 我們解決什麼問題？

一個人自己運動時，常常不容易知道「我做了幾下」、「動作有沒有做到位」或「長期有沒有進步」。PersonAI 把這些資訊整理成即時提示與個人紀錄，讓訓練過程更容易觀察。

> **專題背景待團隊補充：** 為何選擇此題目、實際服務對象、訪談或測試結果、合作單位、量化成果。沒有證據前，不要在簡報或文件中宣稱成效。

### 重要界線

- PersonAI 是**訓練輔助工具**，不是醫療診斷、復健處方或保證運動安全的系統。
- 目前程式明確支援的動作是 **深蹲（squat）** 和 **伏地挺身（pushup）**。
- 相機影像在瀏覽器內做姿勢辨識；後端收到的是 33 個座標與分析所需資料，不是原始影片。
- 個人 InBody 與運動紀錄需要登入後才可讀寫；後端會從登入憑證確認「這是哪位使用者」，不接受前端自己填使用者 ID。

## 前端畫面和後端 API 怎麼配合？

把前端想成「餐廳的點餐櫃檯」，後端是「廚房」，API 是兩者共用的點餐單。前端只能按照點餐單的路徑、方法與資料格式提出需求；後端回傳結果後，前端再把它顯示給使用者。

| 使用者看到的地方 | 前端主要位置                                                 | 呼叫的介面                                             | 後端做的事                                               |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------ | -------------------------------------------------------- |
| 登入／註冊       | `src/app/login`、`src/app/register`                          | Better Auth 的 `/api/auth/*`                           | 建立或驗證登入狀態，前端取得 JWT 給 API 使用             |
| 首頁儀表板       | `src/app/page.tsx`                                           | `GET /wk/me`、`GET /wk/me/daily`                       | 讀取該登入者的訓練紀錄與每日摘要                         |
| 即時分析         | `src/app/analyze/page.tsx`、`src/hooks/use-pose-analysis.ts` | `WS /ws/analyze/{exercise_type}?weight_kg=...`         | 驗證連線，分析 33 個姿勢點，回傳角度、次數、錯誤與卡路里 |
| 儲存訓練         | 同上                                                         | `POST /wk/me/record`                                   | 儲存本次訓練，並計算姿勢分數                             |
| 訓練紀錄         | `src/app/history/page.tsx`                                   | `GET /wk/me`、`GET /wk/me/summary`、`GET /wk/me/daily` | 回傳列表、動作統計與每日統計                             |
| InBody 資料      | `src/app/inbody/page.tsx`                                    | `GET /inbody/me`、`POST /inbody/me`                    | 讀寫身體組成，回傳 BMI、BMR、瘦體重等摘要                |
| 卡路里試算       | `src/components/inbody/calorie-estimator.tsx`                | `POST /inbody/me/calories`                             | 依已儲存的身體資料、動作、時間與強度試算                 |
| 後端是否活著     | `src/lib/api.ts`                                             | `GET /server`                                          | 回傳伺服器健康狀態                                       |

### 即時分析的資料來回

```text
相機影像
  ↓（只在瀏覽器）
MediaPipe Pose 找出 33 個關鍵點
  ↓（每一幀的 JSON，包含 frame_id）
WebSocket /ws/analyze/squat 或 /ws/analyze/pushup
  ↓
後端：驗證 JWT 與網頁來源 → 角度計算 → FSM 動作狀態 → 錯誤偵測 → 卡路里
  ↓（同一個 frame_id、處理時間、結果）
前端：顯示次數、角度、提示、卡路里；停止時再用 REST API 儲存紀錄
```

### 你不需要背的 API 細節

- `/me` 的意思是「目前登入的這位使用者」，不是要你在網址或表單中填 ID。
- `GET` 是讀資料；`POST` 是送資料讓後端建立或更新。
- WebSocket 是持續開著的雙向通道，適合一秒傳多次的姿勢點；一般 REST API 則適合一次讀寫，例如儲存訓練結果。
- 前端的 `src/lib/api.ts` 負責把前端常用的 camelCase 欄位與後端的 snake_case 欄位互相轉換。新增欄位時，不要在畫面元件各自亂轉名稱。

## 小小字典

| 名詞               | 用小朋友也懂的話說               | 你實際要做什麼                                     |
| ------------------ | -------------------------------- | -------------------------------------------------- |
| 前端（Web）        | 使用者看得到、按得到的網頁       | 在 `personai-web` 找頁面、元件與畫面文字           |
| 後端（API）        | 處理規則、保存資料的服務         | 在 `personai-api` 找 router、model、service 與測試 |
| API                | 前端跟後端約好的溝通規則         | 先確認路徑、GET/POST、要傳什麼、會回什麼           |
| 資料庫             | 保存帳號、InBody、訓練紀錄的櫃子 | 不直接改正式資料；先用測試或本機資料驗證           |
| JWT                | 登入後取得的短期通行證           | 不貼到聊天室、截圖或 GitHub；遇到問題重新登入      |
| WebSocket          | 保持開著、可持續互傳訊息的電話線 | 用於即時姿勢分析；確認動作類型、登入與連線狀態     |
| Git                | 記錄檔案版本的時光機             | 每次只放一個小主題的變更                           |
| Branch（分支）     | 時光機裡的一條工作支線           | 每個功能或 bug 開一條新分支，不直接改 `main`       |
| Commit             | 幫一小段完成的工作存檔           | 寫清楚「這一次到底做了什麼」                       |
| Pull Request（PR） | 請夥伴檢查並合併你的工作         | 說明目的、測試方式、截圖與還不知道的風險           |
| 測試               | 用固定步驟確認沒有弄壞東西       | 修改前想好成功畫面；修改後實際跑指令與手動操作     |

## 第一次在自己電腦跑起來

> 這些步驟是本機開發用。`.env`、密碼、JWT、資料庫連線字串都不能 commit、不能貼到公開 PR，也不要傳給 AI。

### 0. 先準備

- 安裝 Git 與 [GitHub Desktop](https://desktop.github.com/)。
- 安裝 Bun（前端使用）、Python 3.11 以上與 Hatch（後端環境管理）。
- 用 GitHub Desktop clone **personai-web** 與 **personai-api** 兩個倉庫到相鄰資料夾。
- 向負責設定的人索取「安全的 `.env.example`／環境變數說明」，自己建立本機設定；不要索取或傳送正式環境密碼。

### 1. 啟動後端 API

在 `personai-api` 根目錄開終端機。Hatch 會依 `pyproject.toml` 建立並使用專案的預設 Python 環境，所以不要在這個專案改用 `pip install -e .`：

```bash
hatch run fastapi dev src/personai_api/main.py
```

第一次執行時，Hatch 會先準備環境與依賴，請耐心等它完成。正常時 API 預設在 `http://localhost:8000`。先用瀏覽器開 `http://localhost:8000/docs`，或開 `http://localhost:8000/server`；健康檢查應回傳「伺服器正常運作」。

### 2. 啟動前端網站

在另一個終端機、`personai-web` 根目錄執行：

```bash
bun install
bun run dev
```

開啟終端機顯示的網址（通常是 `http://localhost:3000`）。先註冊測試帳號，再依序確認：

1. 首頁能進入且登入狀態正常。
2. InBody 頁能儲存基本資料。
3. 即時分析頁允許相機權限；選深蹲或伏地挺身後可開始訓練。
4. 停止訓練後顯示「本次訓練已儲存」。
5. 訓練紀錄頁能看見剛才的資料。

### 3. 連不上時，先做這三件事

1. 看兩個終端機是否都還在執行，且沒有紅色錯誤。
2. 確認前端是 `localhost:3000`、API 是 `localhost:8000`；不要先改程式碼或 CORS。
3. 在瀏覽器按 `F12` → **Network**，點失敗請求，記下 Request URL、Request Method、Status Code、Response Headers 與 API 終端機日誌。遮住 Token、Cookie 與密碼後再回報。

### 特別情況：看到 `failed to fetch` 或 `OPTIONS ... 405`

這不表示「把 CORS 全部打開」就會好。`405 Method Not Allowed` 通常代表請求方法和 API 合約不一致，或電腦上執行的是舊的／錯的 API 行程。

請照既有的 [CORS 夥伴測試說明](../CORS_夥伴測試說明.md) 做，並回傳完整但已遮蔽敏感資訊的輸出。核心檢查是：

```bash
curl -i -X OPTIONS http://localhost:8000/wk/me \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: authorization,content-type"
```

預期會得到 `200 OK` 與 `access-control-allow-origin: http://localhost:3000`。若得到 `405` 且 `Allow: GET`，先確認正在執行的 API 專案、啟動指令與終端機日誌；**不要**未經證據就擴大允許來源或方法。

## 想新增功能時：照這張清單做

### 例子：想新增「訓練完成鼓勵訊息」

先不要急著叫 AI 寫程式。先把下列內容寫在 GitHub Issue、PR 說明或團隊記事中：

```text
使用者故事：使用者停止訓練並成功儲存後，看見一則鼓勵訊息。
完成條件：
- 成功儲存時顯示訊息。
- 儲存失敗時不顯示成功訊息，而是顯示錯誤。
- 深色模式與手機寬度下不被切掉。
不做的事：不改後端資料格式、不新增推播通知。
```

### 新功能流程

1. **找位置。** 先用畫面找到頁面，再找對應檔案。例如即時訓練在 `src/app/analyze/page.tsx`；若要新增資料，先看 `src/lib/api.ts` 和後端 router。
2. **確認是否需要 API。** 純畫面改動通常只改前端；要永久保存、計算或跨裝置共用資料，才需要前後端一起改。
3. **先說清楚 API 合約。** 若要新增欄位，寫下路徑、方法、送出的 JSON、回傳 JSON、錯誤情況；前後端同意後再開始。
4. **建立分支。** 例如 `feat/training-success-message`，一個分支只處理一個主題。
5. **小步修改。** 先完成最小可見結果，再補錯誤處理與測試；不要同一個 PR 順便大改版面或更新無關套件。
6. **自己驗收。** 用完成條件逐項操作；若有畫面變更，至少看桌機與手機寬度、深色模式、瀏覽器 Console。
7. **跑檢查。** 依改動範圍執行下方的測試指令。
8. **commit、推送、建立 PR。** PR 要讓沒參與的人也能理解目的與驗證方式。
9. **請人檢查。** 回答 review 問題後再合併；合併完同步 `main`，確認線上流程沒有被破壞。

### 新 API 的最小約定範本

```text
目的：使用者可以 ______。
前端畫面／檔案：______。
方法與路徑：POST /______。
登入：需要／不需要（原因：______）。
前端送出：{ "...": "..." }。
後端回傳：{ "...": "..." }。
成功時畫面：______。
失敗時畫面：______。
測試案例：正常值、缺少欄位、未登入、重複操作。
```

## 發現 bug 時：先留下好線索

Bug 回報不是「壞掉了」。好的回報讓另一位夥伴能在自己的電腦重現問題。

### Bug 回報範本

```text
標題：停止訓練後，訓練紀錄沒有出現在歷史頁
環境：macOS / Chrome 版本 / 前端與 API commit 或分支
前置條件：已登入、已填 InBody 資料
重現步驟：
1. 開啟 /analyze
2. 選深蹲並開始 10 秒
3. 按「停止並儲存」
4. 前往 /history
預期結果：看到剛剛的訓練紀錄
實際結果：顯示「資料載入失敗」
證據：截圖、Network 的 Request URL/Method/Status、前端與 API 終端機日誌
敏感資訊：Token、Cookie、密碼已遮蔽
```

### 修 bug 流程

1. **重現一次。** 先確認不是網路、登入或沒有啟動 API。
2. **縮小範圍。** 看畫面有沒有觸發請求；有請求就看 API 回應；沒有請求就先查前端事件與狀態。
3. **寫修正目標。** 例如「未登入時不送出儲存請求，並顯示登入提示」，不要只寫「修一下」。
4. **建立 `fix/...` 分支。** 把重現步驟變成手動檢查或自動測試。
5. **修正後重跑原步驟。** 還要確認相近功能沒有壞掉。
6. **PR 中保留問題、原因、解法與驗證證據。** 若原因還不確定，要誠實標示「暫時假設」。

## GitHub Desktop 與 GitHub 網頁操作

### 每次開始前：同步，不覆蓋別人的工作

在 GitHub Desktop：

1. 左上角選擇正確倉庫（`personai-web` 或 `personai-api`）。
2. 確認目前分支不是別人的功能分支。
3. 按 **Fetch origin**；若出現 **Pull origin**，按它把遠端新內容抓下來。
4. 先看 **Changes** 是否已經有不屬於你的檔案；有的話先詢問原作者，不要任意丟棄。

### 建立分支、commit、推送

1. 按 **Current Branch** → **New Branch**。
2. 使用小寫英文與連字號，例如 `feat/inbody-export`、`fix/history-load-error`、`docs/team-handbook`。
3. 修改後，在 **Changes** 逐個看 diff：只勾選這次工作需要的檔案。
4. 在左下填寫 Summary（commit message）；Description 可補充原因。
5. 按 **Commit to 分支名稱**。
6. 按 **Publish branch** 或 **Push origin**。

### GitHub 網頁直接修改與 commit（只適合小型文件修正）

GitHub 網頁不能取代本機開發環境：它不能讓你啟動相機、跑完整測試或安全地處理大量程式碼。不過改 README、拼字或本手冊時，可以這樣做：

1. 到正確倉庫與正確分支，打開要修改的檔案。
2. 按右上角鉛筆圖示 **Edit this file**，修改後先按 **Preview changes** 檢查 Markdown。
3. 往下找到 **Commit changes**，填入合規的英文 commit message。
4. 選 **Create a new branch for this commit and start a pull request**，不要直接 commit 到 `main`。
5. 按 **Propose changes**，接著填 PR 說明、指定 reviewer，依下節流程完成審查。

> 只要改動包含 TypeScript、Python、API 或畫面互動，就回到 GitHub Desktop／本機做，因為你必須能執行與測試它。

### 從 GitHub 網頁建立 PR

1. 推送後到 GitHub 倉庫頁，按 **Compare & pull request**；或開 **Pull requests** → **New pull request**。
2. Base 選 `main`，Compare 選你的分支；確認方向沒有反過來。
3. 標題用一句話說明改動；內文套用以下範本。
4. 指定 reviewer、加上合適 label；不要自己合併需要他人審查的 PR。
5. Review 有意見時，在同一分支修正、commit、push；PR 會自動更新。
6. 合併後回 GitHub Desktop 切回 `main`，再按 **Pull origin**；確認功能分支已不再需要後才刪除本機分支。

### PR 範本

```md
## 目的

這個 PR 解決／新增什麼？

## 變更

- （請填寫）

## 驗證方式

- [ ] `bun run lint` 或 `hatch run test`
- [ ] 手動操作：
- [ ] 畫面截圖（若有 UI 變更）

## 風險／尚未確認

- 無／
```

## Commit message 規範

格式固定為：

```text
type(scope): description
```

- `type` 用小寫：`feat` 新功能、`fix` 修 bug、`docs` 文件、`test` 測試、`refactor` 重構、`chore` 工具或維護。
- `scope` 說明影響區域，例如 `analyze`、`history`、`api`、`docs`。
- `description` 使用簡短英文、祈使句，不加句點。它要描述這次 commit 做了什麼，不是描述心情。
- 一個 commit 只放一個可以獨立說明的小主題。不要把「功能、格式化、刪除檔案、套件升級」全部混在一起。

| 類型   | 可直接改字使用的範例                                                                              |
| ------ | ------------------------------------------------------------------------------------------------- |
| 新功能 | `feat(analyze): show training completion message`<br>`feat(inbody): add calorie estimation input` |
| 修 bug | `fix(history): handle empty workout summary`<br>`fix(socket): report server connection errors`    |
| 文件   | `docs(handbook): add beginner development guide`<br>`docs(api): clarify workout record payload`   |
| 測試   | `test(auth): cover invalid registration email`<br>`test(workout): verify daily summary response`  |

### 不要這樣寫

```text
update files
fix stuff
final version
我的修改
```

這些訊息看不出改了什麼，也讓日後找問題非常困難。

## 測試：修改後至少做什麼？

測試不是「跑過一次就一定沒問題」，而是留下可重複確認的證據。根據你的變更選擇：

| 修改內容               | 先跑的檢查                                          | 還要手動確認                                              |
| ---------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| 前端 TypeScript／React | `bun run lint`、`bun run typecheck`、`bun run test` | 對應頁面、登入／未登入、手機寬度、深色模式、Console       |

## 用 AI 協助開發，但不把責任交給 AI

AI 可以像很快的助教，卻不會自動知道我們的最新程式、需求、密碼、安全限制或專題事實。你仍然是要負責的人。

### AI 適合幫什麼

- 用白話解釋一段程式或錯誤訊息。
- 根據明確需求列出實作計畫、測試案例、Issue 或 PR 草稿。
- 在小範圍內協助寫元件、測試或重複性程式，並解釋每一段用途。
- 檢查 commit message 是否符合規範，或檢查你是否漏了錯誤處理。

### AI 不可以替你做的判斷

- 不可把 `.env`、密碼、JWT、Cookie、個資、正式資料庫連線字串貼給 AI。
- 不可要求 AI「整個專案全部重寫」或直接把大量輸出不看就貼上。
- 不可把 AI 猜測的醫療、隱私、效能或使用者成效當成專題事實。
- 不可因 AI 說「改 CORS」就直接修改設定；先照 CORS 排查流程取得證據。

### 問 AI 的好範本

```text
我是 PersonAI 專案的新手。我要修改 [檔案路徑] 的 [具體功能]。
目前行為：______。
我希望變成：______。
不能改的部分：API 路徑、登入方式、資料庫 schema。
完成條件：______。

請先用繁體中文解釋相關程式的資料流，列出最小修改計畫、風險與測試步驟。
不要輸出完整重寫；若資訊不足，請明確指出缺少什麼。
```

### AI 回答後的人工檢查

1. 它有沒有真的對應到目前檔案與 API？
2. 它有沒有意外刪掉錯誤處理、登入檢查或型別？
3. 它是否要求你貼密碼或改動無關檔案？若有，停止。
4. 你能不能用自己的話解釋每一段要合併的程式？不能就先請 AI 解釋。
5. 你有沒有實際跑測試與手動操作，而不是只相信 AI 的文字？

## 專題展速讀區

### 30 秒介紹

> PersonAI 是一個 AI 健身教練網頁。使用者登入後，可以用相機進行深蹲或伏地挺身訓練。瀏覽器先用 MediaPipe 將人體動作轉為 33 個姿勢關鍵點，再透過 WebSocket 傳給 FastAPI 後端。後端進行角度計算、動作階段判斷、姿勢提示、次數與卡路里估算；完成後，使用者可在首頁、InBody 與訓練紀錄中查看自己的資料與趨勢。

### 2 分鐘架構講稿

1. **使用者層。** 使用者註冊登入，才能存取自己的 InBody 與訓練資料。
2. **前端層。** Next.js 網頁提供首頁、即時分析、訓練紀錄與 InBody 頁面。即時分析時，MediaPipe 在使用者瀏覽器中讀取相機並取得 33 個關鍵點。
3. **即時通訊層。** 前端使用 WebSocket 把關鍵點送往後端，也立即收到分析結果。這比反覆建立一般 HTTP 請求更適合連續的姿勢資料。
4. **後端層。** FastAPI 先驗證登入憑證與來源，再用生物力學服務計算關節角度、有限狀態機（FSM）與姿勢錯誤；它也負責 InBody、卡路里與運動紀錄 API。
5. **資料與隱私。** 個人資料依登入使用者區隔。相機原始影像不會被傳到後端；但仍應清楚告知使用者資料處理方式，並避免把憑證或個資放進展示畫面。

### 常見提問與誠實回答

**Q：AI 在這個專案裡到底做了什麼？**<br>
A：目前「看見人體姿勢」的部分使用 MediaPipe Pose；後端根據關鍵點用角度計算、FSM 狀態機與規則偵測分析動作。它不是宣稱用大型語言模型診斷人體，也不是醫療系統。

**Q：為什麼需要 WebSocket？**<br>
A：姿勢分析需要連續傳送每一幀的關鍵點並即時取得回覆。WebSocket 維持一條雙向連線，較適合這種互動；儲存與查詢紀錄則使用一般 REST API。

**Q：後端有收到使用者相機影片嗎？**<br>
A：目前程式流程是在瀏覽器內透過 MediaPipe 處理影像，傳給後端的是 33 個姿勢關鍵點與分析所需資料，而不是原始影片。

**Q：如何保護使用者資料？**<br>
A：受保護的 API 以 JWT 驗證目前使用者，後端從憑證中的使用者身分讀取資料，而不是相信前端自填 ID。敏感憑證不能出現在 Git、截圖或公開文件。

**Q：目前支援什麼？**<br>
A：程式明確支援深蹲與伏地挺身、InBody 基本計算、訓練紀錄與統計。其他運動、正式部署效果、使用者成效或醫療適用性，若尚無測試證據就不能當作已完成宣稱。

**Q：如果 API 失敗怎麼辦？**<br>
A：先確認 Request URL、方法、回應狀態碼與後端日誌。405 要先比對 API 合約與實際執行的行程；不能直接把 CORS 開到最大。
